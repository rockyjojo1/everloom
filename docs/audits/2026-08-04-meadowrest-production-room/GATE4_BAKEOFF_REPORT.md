## Root causes found and fixed

The previous attempt's ~12 FPS reading and "1 failed asset" were both real
measurements of real bugs — just not the bugs it thought they were.

### Performance: ~12 FPS → 60 FPS

Three independent, compounding causes, found by actually profiling rather
than tuning thresholds:

1. **Headless Chromium's software rasterizer.** `chromium.launch()` with no
   args defaults to SwiftShader (CPU-based WebGL). Confirmed via
   `WEBGL_debug_renderer_info`: `SwiftShader (Subzero)` vs this machine's
   real `Intel(R) UHD Graphics`, 12–17 FPS vs 60 FPS on the identical scene.
   Fixed by adding `--use-gl=angle --use-angle=d3d11
   --ignore-gpu-blocklist --enable-gpu-rasterization` to both
   `playwright.config.ts` and `capture-production-room.mjs`.
2. **A React state update on every animation frame.** `setMetrics()` was
   called inside the `requestAnimationFrame` loop, forcing a full React
   re-render 60×/sec purely to refresh a debug overlay. Throttled to every
   250ms; `window.__EVERLOOM_BAKEOFF__` (what tests/capture actually read)
   is still written every frame inside `updateMetrics()`, independent of
   React state.
3. **An orphaned second WebGL context from React 18 StrictMode.** In dev
   mode, StrictMode mounts, cleans up, and re-mounts effects. The discarded
   first mount had no `mounted` guard before renderer creation, so it fully
   created a second `WebGLRenderer`, loaded all 21 assets a second time, and
   appended a second canvas to the DOM — silently, since its own render
   loop correctly self-cancelled and never painted anything. The orphaned
   GPU context was never disposed and sat there contending with the real
   one for the rest of the session. Added the missing guard.

### The "1 failed asset": town.cottage was never broken

The actual failing runtime asset ID, read directly from
`metrics.failedAssetIds`, was `nature.rock-small-b` — an asset ID with no
entry in `packages/assets/src/registry.json` at all (confirmed by
cross-referencing every ID the layout uses against the registry). It was a
typo in the decorative "additional rocks" list, unrelated to
`town.cottage`. Fixed to `nature.rock-large`. `town.cottage` was restored
to its required core placement (it had been wrongly swapped for
`nature.oak` in the previous attempt) and loads correctly — it was never
the actual problem.

A regression test now exists specifically to catch this class of bug:
`src/bakeoff/productionRoomLayout.test.ts` asserts every `runtimeAssetId`
the layout references resolves in the canonical registry.

### Interaction state: currentPlayerAnimation was structurally dead code

`window.__EVERLOOM_BAKEOFF__.currentPlayerAnimation` was never written
anywhere outside its `"Idle"` constructor default. The pointer-down handler
correctly crossfaded the real Three.js `AnimationAction` but never touched
`metricsRef`, so the *exposed* metric was permanently stuck at `"Idle"`
regardless of what was actually animating on screen. This is why the
previous attempt's `Walking_A` assertions failed even after supposedly
"fixing" movement — movement itself worked; only the metric was dead.
Fixed by writing `"Walking_A"` in the pointer handler and `"Idle"` on
arrival. `movementTarget` had the same class of bug (never cleared on
arrival) and is fixed the same way. `playerPosition` was only synced while
actively moving, going stale after Reset View; now synced every frame.

### Visual correctness: characters were never actually tinted

Found by inspecting the capture screenshots per the Phase 12 checklist:
player, Mara, and the skeleton all rendered in the same untinted grey/silver
colour. The tint-application code checked `child.material instanceof
THREE.MeshPhongMaterial`, but `GLTFLoader` produces `MeshStandardMaterial`
for these rigs (confirmed by the same pattern already in use in
`world/assets.ts`). The `instanceof` check silently matched nothing. Fixed
to check the correct material type and clone+multiply the colour (same
pattern as `assets.ts`).

## Capture script fixes

`capture-production-room.mjs` previously failed outright (wrong relative
path for output, `chromium.launch()` with no GPU args, a Windows
`spawn(shell:false)` `ENOENT`, and a port-liveness check that matched
TIME_WAIT client sockets as "in use"). All fixed; the script now runs
successfully and exits 1 if any hard requirement fails (previously always
exited 0 regardless of outcome). It also now records WebGL renderer/vendor,
browser version, page/console-error and 404 counts, and full measurement
provenance in `METRICS.json`, and captures mobile screenshots at
`deviceScaleFactor: 1` so PNG pixel dimensions exactly match the required
CSS viewport sizes (previously produced 2532×1170 instead of 844×390 at
`deviceScaleFactor: 3`).
